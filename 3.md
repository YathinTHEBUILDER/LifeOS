## 1. Recurring tasks & events (highest priority — schema exists, logic doesn't)

**Problem:** `Task.recurrence_rule` and `CalendarEvent.recurrence_rule` are defined
in `src/types/index.ts` and exist as columns in `supabase/schema.sql`, but nothing
in the codebase reads or writes them. Recurrence is a no-op today.

**Files:**
- `src/types/index.ts` — `recurrence_rule` currently `string | null`. Tighten to a
  union: `'daily' | 'weekdays' | 'weekly' | 'monthly' | null` (matches the SQL
  comment in `schema.sql` line 67) or design a small RRULE-lite object if you want
  custom intervals — keep it simple, this app doesn't need full iCal RRULE.
- `src/lib/store/planner-context.tsx` — add a `generateRecurringInstances(task, rangeStart, rangeEnd)`
  helper. Simplest correct approach: don't materialize every future instance in
  the DB. Instead, store one canonical task/event row with `recurrence_rule` set,
  and have the Calendar/Today views expand it into virtual occurrences for display
  (similar to how Google Calendar handles recurring events client-side before you
  edit a single instance). Completing a specific occurrence should log a
  completion keyed by `(task_id, occurrence_date)` rather than mutating the
  canonical row — you'll likely want a small `task_completions` table
  (`task_id`, `date`, `completed_at`) for this, or reuse the existing
  `habit_logs` pattern as a model.
- `src/components/tasks/quick-add-modal.tsx` and `src/components/tasks/task-manager.tsx`
  — add a recurrence picker (Daily / Weekdays / Weekly / Monthly / None) to the
  task creation/edit UI.
- `src/components/calendar/calendar-view.tsx` — expand recurring events into
  visible occurrences within the visible date range only (don't precompute the
  whole future).

**Acceptance check:** create a "daily" task, confirm it shows up on today and
tomorrow's Calendar/Today view, and completing today's occurrence doesn't affect
tomorrow's.

## 2. Habit frequency-aware streaks

**Problem:** `getHabitStreak` in `planner-context.tsx` treats every habit as
requiring completion every single day, but `Habit.frequency` already supports
`'daily' | 'weekdays' | 'weekly' | 'custom'` (see seed data — `habit-3` is
`weekdays`). A `weekdays` habit currently shows a broken streak every weekend.

**Files:**
- `src/lib/store/planner-context.tsx` — rewrite `getHabitStreak(habitId)`:
  - `daily`: unchanged (current logic is correct).
  - `weekdays`: skip Sat/Sun when checking for a break — a missed weekend should
    not zero the streak.
  - `weekly`: streak counts consecutive *weeks* where at least `target_days`
    logs exist within that week (use `startOfWeek`/`endOfWeek` from `date-fns`,
    already imported elsewhere in the file).
  - `custom`: treat like `daily` for now (no custom day-of-week selection exists
    yet — out of scope unless you also add that to the Habit model).
- `src/components/habits/habit-manager.tsx` — the 7-day matrix currently renders
  every day as togglable regardless of frequency. For `weekdays` habits, gray out
  (but don't hide) weekend cells so it's visually clear they don't count against
  the streak.

**Acceptance check:** a `weekdays` habit logged Mon–Fri, skipped Sat/Sun, should
still show an unbroken streak on Monday.

## 3. Habit weekly/monthly heatmap view

**Problem:** the only view is a 7-day matrix in `habit-manager.tsx`. No way to see
longer-term consistency.

**Approach:** add a toggle (7-day / 90-day) that switches the matrix for a
GitHub-contributions-style heatmap using existing `habitLogs` data — no new
backend needed, this is a pure frontend read. Reuse `eachDayOfInterval` from
`date-fns` (already used in `habit-manager.tsx`) with a longer range, and render
as a CSS grid of small colored squares instead of the current row of day-buttons
for the 90-day mode.

**Files:** `src/components/habits/habit-manager.tsx` only.

## 4. Data export/import (safety net given sync is fire-and-forget)

**Problem:** `settings-view.tsx` already has `handleExportData` (JSON export) —
good. There's no import counterpart, and no re-sync/retry mechanism for writes
that failed while offline (a known limitation from the sync work: failed writes
are dropped, not queued).

**Files:**
- `src/components/settings/settings-view.tsx` — add an "Import JSON" file input
  next to the existing export button. Parse the same shape `handleExportData`
  produces, and call the existing context actions (`addTask`, `addHabit`, etc.)
  for each record rather than writing to localStorage directly, so imported data
  syncs to Supabase the same way manually-created data does.
- Consider a minimal write queue in `planner-context.tsx`: on `syncInsert`/
  `syncUpdate`/`syncDelete` failure, push `{ table, op, payload }` into a
  `pendingSyncQueue` array (persisted to localStorage under a new key), and
  drain it on next successful auth check or on a `window.addEventListener('online', ...)`
  handler. This is the fix for the "fire-and-forget" caveat flagged after the
  Supabase wiring — worth doing before relying on this in daily use.

## 5. Notifications for habits & time-blocked events

**Problem:** `public/sw.js` (service worker) exists and does offline asset
caching, but has no push/notification logic. `Task.due_time` and
`CalendarEvent.start_time` exist but nothing reminds the user.

**Approach (simplest version, no server push infra needed):** client-side
`Notification` API + `setTimeout`, scheduled per-session from
`src/lib/store/planner-context.tsx` or a new `src/lib/notifications.ts`:
- On app load (and whenever `events`/`habits` change), compute upcoming
  event start times and any habit "reminder time" (you'll need to add an
  optional `reminder_time` field to `Habit` if you want per-habit reminders —
  otherwise default to a single daily reminder time from `UserProfile`).
  Schedule `setTimeout` calls to fire `new Notification(...)` for anything
  within the next ~12 hours; this only works while a tab is open.
- For real background push (works when the app/tab is closed), you'd need
  Web Push (VAPID keys + a `push` event handler in `public/sw.js` + a
  `push_subscriptions` table in Supabase to store each device's subscription).
  This is a bigger lift — flag it as a stretch goal, don't block the
  session-based version on it.

**Files:** `public/sw.js`, new `src/lib/notifications.ts`,
`src/lib/store/planner-context.tsx` (call the scheduler on data change),
`src/components/settings/settings-view.tsx` (permission request UI + toggle).

## 6. Weekly/monthly Review rollups

**Problem:** `src/components/review/daily-review-view.tsx` and the
`DailyReview` type/table only support single-day retrospectives. No aggregation
exists across a week or month even though all the underlying data
(`tasks`, `focusSessions`, `habitLogs`, `dailyReviews`) is already available in
context.

**Files:**
- `src/app/review/page.tsx` and `src/components/review/daily-review-view.tsx` —
  add a view-mode toggle (Day / Week / Month). For Week/Month, don't add new DB
  tables — just aggregate client-side from existing `dailyReviews`, `tasks`
  (completed count + on-time rate), `focusSessions` (total minutes), and
  `habitLogs` (completion % per habit) over the selected range.
- Good chart candidates: completion rate trend line, focus-minutes-per-day bar
  chart, habit consistency % per habit. No new dependency needed if you keep it
  simple — this repo doesn't currently include a charting library, so either add
  a lightweight one (e.g. `recharts`) or build simple CSS/SVG bar charts inline.

## Constraints to respect

- Keep the local-first pattern: every mutation should update React state +
  localStorage synchronously, with Supabase writes as an async, non-blocking
  fire-and-forget (matching the existing `syncInsert`/`syncUpdate`/`syncDelete`
  helpers already in `planner-context.tsx`) — don't make the UI wait on a
  network round trip for anything.
- Don't break the anonymous/local-only demo mode — every feature must still work
  with no Supabase env vars configured, falling back to localStorage only.
- Match existing code style: Tailwind utility classes, `lucide-react` icons,
  `sonner` for toasts, `date-fns` for date math — don't introduce new libraries
  for things the existing stack already covers.
- Run `npx tsc --noEmit` and `npm run build` before considering any item done.
